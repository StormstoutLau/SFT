## 2. 成立项

### 成立 1 — 发现 1 + 8（同族）：主结论处不用自己声明的降级 ★★ 本仓第六次犯同一形态

审查者指出：「Unsloth Studio 在 gfx1151 上真开箱」被标 **A 级**并写进 §3.1 结论、§4.1 定位、§6.1 方案输入，而同一文档的 **§2.1 / §4.3 / §5.2 / §6.4 四处**都明写「未取证 / 未验证 / E4 判断，不作判据」。且把「官方支持 LoRA 内核」（U1，已验）**偷换**为「Studio 全链路 UI 可用」（未验）。

**判定：完全成立。** 这是 P-005 成立 1「声明降级未传播」的**第六次复发**——前五次分别是：RESEARCH 的 B9、DESIGN 的 §5.1 容量、A-1 的三处容许带……

★ **元判断：反复复发说明缺的不是自觉，是机械检查。** 我在每份文档里都写了「本档自我约束要防这条」，然后每次都犯。⇒ 见 §5 的门禁化建议。

**处置**：主结论改为「**训练器商品化，但 Studio UI 在 gfx1151 的可用性未验 ⇒ 主路径按库脚本设计，Studio 作可选加速**」，与 B-1 倾向一致（原文明写「倾向：库路径优先」，主结论却没同步——审查者抓的正是这个不一致）。

### 成立 2 — 发现 2：abstract 级被当 A 级事实用

L1-L6 六条全标 A 级，但依据全是 abstract。审查者指出：abstract 常含简化/夸大，**最多支撑 B 级（推断类）**且须显性标注未读正文。我在 §5.2 自认「数值细节不得作阈值」，却在 §3.2/§6.2 把 L1/L3/L4 转成「必须按域切」「必须等算力」等阻断性约束。

**判定：成立。** abstract 引文本身可核（这部分是 A），但**由它推出的工程约束是 B 级推断且跳步**。⇒ 六条定级 A→B，约束措辞「必须」降为「依据 X，候选做法」。

### 成立 3 — 发现 3：GRPO 的 matched-compute 被零成本迁移到 SFT+合并 ★ 本轮技术含量最高

L3 论文研究的是 **GRPO**（含 rollout 采样、reward 计算、多轮策略更新），其「等 token 预算」结论被本档直接用作 SFT+LoRA 合并的评估协议。两者预算量纲不同：SFT 无 rollout、无 reward model，「生成 token 数」在 SFT 语境通常指训练集 token。

**判定：成立，且是标准形态 III**（证据全对、综合推理错）。我 §4.3-3 自己写了「搬到 SFT+合并需重新定义预算单位」，却在 §6.2 把「评估必须等算力（L3）」当约束、B-3 直接「倾向按生成 token 数计（L3 用的正是这个）」——**明知不可迁移却照抄了单位**。

### 成立 4 — 发现 4：Lean 池的在线指标被用来论证离线强项

用「0.54 GB/会话、11.7 ms/tactic」（在线低延迟推理画像）论证数据过滤器「★ 强」。离线批量过滤涉及接口重构、吞吐压测、错误分流、编译缓存失效，**无一项有实测**。

**判定：成立。** ⇒ §4.2 的「★ 强」改「◐ 潜力未验」，并新增空白项。

### 成立 5 — 发现 5：L5 是蒸馏不是 SFT，且「1.5B 可负担」无据

L5 研究蒸馏、实验在 A100/H100；本档据此定「目标模型 ≤7B」，而本集群 MFU/tokens-per-sec **从未实测**（P-002/P-006/P-008 三批都没量）。

**判定：成立。** ⇒ 模型规模倾向标「无实测依据，待 A-4 基准后定」。

### 成立 6 — 发现 6：L1 只证「混合有干扰」，未证「按域切+合并能消除干扰」

替代解释未讨论：课程学习、域加权采样、adapter 路由都可缓解干扰且不需硬切分。本档把单篇结论升为「必须」，还在分片阶段预先排除混合，**收窄了设计空间**。

**判定：成立。** ⇒ 「必须按域切」改为三条候选并列，标注均未在本集群验证。

### 成立 7 — 发现 7：程序执行验证 ≠ 形式化验证 ★ 审查者的专业贡献

PaD 用 Python 执行结果过滤 CoT；Lean 是形式化验证，机制不同——**`sorry` 可通过编译、可能证明错定理、类型类推断可掩盖逻辑漏洞**。本档把两者统称「可机判」。

**判定：成立，且是审查者本轮最有价值的一条**（它触及本集群真实下游 Auto_Prover 的技术要害）。
⇒ 新增空白：Lean 侧「编译通过 ≠ 语义正确」需专门判据（如 `sorry` 扫描 + axiom 审计——`D:\RPC` 的 Lean 文档里其实有 `sorry-free` 与「build-time audit pins to three standard axioms」的先例可引）。

## 4. 元结论

1. **审查者已能抓住「文档内部声明与结论不一致」这一高阶错误**：发现 1/3 都不是外部事实错，而是「我自己写了 X，结论却用 ¬X」。这类错误同基座自查系统性漏检（本档 §5.3 自查时只标了「未做 RULE-5」，没发现这三处）。
2. **零驳回不等于审查变准**——本批被审文档问题密度可能确实高（六条规律全靠 abstract、主结论单源）。⇒ 不可据此调低对审查者的核验要求。
3. ★ **反复复发的错误形态应当门禁化**（见 §5）。

## 5. 建议新增机械检查（本仓门禁缺口）

本仓已六次犯「声明降级却当结论用」。人工自觉已被证明不可靠 ⇒ 建议加一条校验器检查：

> **同一文档内，凡出现 `[依赖假设 X]` / `未验证` / `E4` / `E5` 标记的条目，其关键词若在结论段（§4 / §6.1 / §6.2）被引用且未带同等降级标记 ⇒ 报 P2。**

落点 = `scripts/` 新增检查（Layer-1 ⇒ T1 批），或先做成 `dc_validator` 的 M6 类规则。
⚠ 该检查有误报风险（元描述语境会含被描述 token，DIS-009 同族），须先做**先验红 + 先验绿**双用例再接门禁。
