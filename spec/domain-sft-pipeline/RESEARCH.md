## 3. 调研发现

### 3.1 问①：Strix Halo 有无开箱即用微调框架

| 候选 | 形态 | 开箱程度 | 级 | 证据 |
|---|---|---|---|---|
| **Unsloth Studio**（已装 A 站） | 无代码 UI：Data Recipes 可视化数据流 + 训练监控 + **导出 GGUF/vLLM/HF 一键回推理** | ★★★ **最接近开箱**，且训练→部署闭环正好接本集群推理侧 | A | E3：`D:\RPC` unsloth-a-station §5.1 + P-008 U1（官方明列 gfx1151 支持 LoRA） |
| Unsloth 库（Python API） | `SFTTrainer` 式脚本 | ★★ 半开箱（要写脚本，但模板齐全） | A | P-008 U9 官方自带 smoke test 参数 |
| **Lean Copilot** | LLM 作 Lean 4 副驾，**可本地运行（含无 GPU）**，MIT | ★★ 对证明场景是现成脚手架，但它是**推理侧**不是训练侧 | A | arXiv **2404.12534v3**（Song/Yang/Anandkumar，2024-04-18 / upd 2025-05-11） |
| LeanPremise / LeanHammer | 神经前提选择 + hammer，比现有 selector 多解 **21%** goals | ★ 模型/工具，非训练框架 | A | arXiv **2506.07477v2**（Zhu et al，2025-06-09 / upd 2026-02-25） |
| llama.cpp `llama-finetune` | 单文件 LoRA | ★ 简陋，且本集群 llama.cpp 不消费 RCCL | B | E3：P-002 B10 |
| 自建 PyTorch + PEFT | 完全自控 | ☆ 无开箱 | C | 本仓 P-006 §5.5 回退路径 |

★ **结论（问①，经 RULE-5 审查修正）**：**训练器已商品化**，但——
⚠ **Unsloth 官方支持的是 LoRA 内核（U1，已验），不等于 Studio 全链路 UI 在 gfx1151 可用（未验）**。
⇒ **主路径按 Unsloth 库脚本设计**（U9 有官方参数），**Studio UI 作可选加速**，与 B-1 倾向一致。
（原结论把二者混为一谈，且把未验项标 A 级——见 `docs/reviews/p010-pipeline.adjudication.md` 成立 1。）
"开箱"即便成立也只覆盖**通用 LoRA 那一段**；对数理/编程/证明场景，**稀缺的不是训练器，是可验证的数据管道**（§3.2）。
⚠ 本结论**单源**（`D:\RPC` 转述 + 官方 `?ask=`），横向对比（Axolotl / LLaMA-Factory / TRL+PEFT 在 gfx1151 的可用性）**完全缺失**（搜索通道 522）⇒ 标 `[单源-待二核]`。

### 3.2 问②：面向数理/编程的细化——社区规律（★ 全部 **B 级**：abstract 已核、**正文未读**，审查成立 2）

| # | 规律 | 级 | 证据 |
|---|---|---|---|
| **L1** | **指令类型存在域干扰**：NLP 下游任务 / 代码 / 通用 chat 三类混合时，"某类对特定应用有利但会损害其他领域" | A | arXiv **2312.10793v3**（Wang et al，2023-12-17 / upd 2024-02-18） |
| **L2** | **合成推理数据含错误推理，会直接毒化蒸馏**；用**程序辅助**（PaD）替代 CoT 可实现合成数据的**自动查错**，小模型因此能超 LLaMA-1 13B | A | arXiv **2305.13888v2**（Zhu et al，2023-05-23 / upd 2024-03-20） |
| **L3** | ★ **评估必须在等算力预算下做**：dense process reward 每次更新领先标准 GRPO，但**按等 token 预算比反而低 14.3 个百分点**——"匹配算力会反转排名"。1668 runs / 6 模型，含 Qwen3-0.6B、Qwen2.5-1.5B | A | arXiv **2611.13560v1**（Singh et al，**2026-11-10**，两天前） |
| **L4** | 挑**预测成功率接近 1/2** 的 prompt 训练，在 matched compute 下提升 1.7 点（Qwen3-0.6B）；且"候选 prompt 预测失败多于一半"这条简单规则在 6 次预注册检验中 5 次预测了增益位置 | A | 同 L3 |
| **L5** | 数学推理可蒸馏进 **sub-billion** 模型（EoTD/ETD，CoT+PoT+EoT 多思路） | A | arXiv **2401.11864v5**（Zhu et al，2024-01-22 / upd 2024-08-01） |
| **L6** | 代码交织推理（NL+代码+**执行结果**）显著提升数学：MathCoder 在 MATH 45.2% / GSM8K 83.9% | A | arXiv **2310.03731v1**（Wang et al，2023-10-05） |

★ **对 L0 的直接含义（这是细化的关键）**：
1. **L1 提示随机 IID 切分有域干扰风险**（三站各训不同域时，合并可能互相损害）。⚠ 但 L1 只证「混合有干扰」，**未证「按域切+合并能消除干扰」**（审查成立 6）⇒ 三条候选并列，均未在本集群验证：① 按域一致性切 ② 课程式难度递进 ③ 域加权采样 / adapter 路由。**不得写成「必须」**。
2. **L2 决定数据管道必须有验证器** —— 数理/代码场景的幸运之处是**答案可机判**（单元测试 / Lean 编译 / 符号计算），这恰好是本集群**已有**的能力：`D:\RPC` 的 **Lean 验证池**（2 站 × 16 会话，边际内存 0.54 GB/会话，11.7 ms/tactic，E1 实测）。⇒ **验证器不需要训练，是现成的算力**。
3. **L3/L4 提示评估协议需改** —— 本仓 P-006 的三臂对照（base/ad_single/ad_merged）**可能不足**：若不做等算力约束，「合并版每步更好」可能是算力假象。⚠ **但 L3 是 GRPO 场景**（含 rollout/reward/多轮更新），其「等 token 预算」**不能零成本迁移到 SFT+合并**（量纲不同，审查成立 3）⇒ **等算力的「思想」可借，「单位」须先重定义**（B-3 由倾向升为**前置任务**）。
4. **L5 说明目标模型可以很小** —— sub-billion 就够装推理能力，而本集群的强项是内存不是算力 ⇒ **小模型 + 高质量可验证数据**是比"微调 120B"更对路的路线。

### 3.3 问③：全流程的形态（数据获取 → 微调 → 测试）

社区无"全流程"单一参考，但各段都有成熟件。综合本集群实况，流程骨架：

```
[1 数据获取]     [2 可验证性过滤]    [3 分片]        [4 训练]         [5 合并]      [6 评估]           [7 导出/上线]
 HF datasets  →  执行/编译/判解  →  按域一致切  →  各站独立 LoRA →  CAT/加权  →  三臂+等算力  →  GGUF→推理侧
 题库/论文       (Lean·pytest·       (L1 依据)      (Unsloth        (L0)        (L3/L4 依据)     (Studio 一键)
                 sympy)                            Studio/库)
```

★ **本集群的个性化优势在 [2] 和 [6]**，不在 [4]：
- [2] 验证器是 CPU/轻 GPU 任务，`D:\RPC` 的 Lean 池已实测可用 ⇒ **数据质量把关几乎免费**
- [6] 等算力评估在小模型上可负担 ⇒ 能做别人做不起的对照实验
- [4] 训练本身是本集群最弱一环（无 RDMA、算力未实测）

## 4. 综合分析

### 4.1 关键发现总结

**"开箱即用"的答案是：训练器有（Unsloth Studio），但全流程没有——而全流程的价值恰好不在训练器那一段。** 对数理/编程/证明，可验证的数据管道 + 等算力评估才是决定成败的环节，本集群在验证器上已有实测能力（Lean 池），这是它相对"租 A100"的真实差异化位置。

### 4.2 landscape：本集群该占哪一段

| 段 | 谁强 | 本集群位置 |
|---|---|---|
| 数据获取 | 与硬件无关 | 中立 |
| **可验证性过滤** | CPU/轻算力密集 | ◐ **潜力未验**——Lean 池实测的是**在线低延迟**画像（11.7 ms/tactic），离线批量过滤的吞吐/接口重构/编译缓存失效**无一项实测**（审查成立 4） |
| 分片策略 | 方法论 | 中立（L1 给了依据） |
| 训练 | 大显存 + 高互联 | ◐ 内存强、互联弱、算力未测 |
| 合并 | 与硬件无关 | 中立 |
| **等算力评估** | 需要大量重复跑 | ◐ **潜力**（三站并行是真优势；「小模型可负担」**无 tokens/sec 实测支撑**，审查成立 5） |
| 导出上线 | 引擎生态 | ★ 强（Studio 直连 GGUF，同集群推理） |

### 4.3 研究空白

1. **Unsloth Studio 的训练 UI 在 gfx1151 上是否真可用**——官方支持 LoRA（U1）与 Studio UI 可用是两件事，本批未取证。
2. **Lean 验证池能否直接当数据过滤器**——它现为证明编排服务，改作数据质检的接口未设计。
3. **matched-compute 协议在 LoRA 合并场景怎么定义"等算力"**——L3 针对 RL 训练，搬到 SFT+合并需重新定义预算单位（★ 已由「倾向」升为**前置任务**，见 B-3）。
4. **Lean 侧「编译通过 ≠ 语义正确」**（审查成立 7）：PaD 的程序执行验证与 Lean 形式化验证机制不同——`sorry` 可通过编译、可能证明错定理、类型类推断可掩盖逻辑漏洞。⇒ 数据过滤若用 Lean，须配 **sorry 扫描 + axiom 审计**双判据（可引 `D:\RPC` 在案先例：数学金融库「no sorry」+「build-time audit pins to Lean's three standard axioms」）。
5. **Lean 池离线吞吐无基准**：现有实测全是在线低延迟画像，批量过滤模式的 样本/秒 未量（审查成立 4）。

## 6. 对设计的输入

### 6.1 可用的技术方案

全流程七段（§3.3），本集群主攻 [2] 验证过滤 + [6] 等算力评估 + [7] 导出闭环，训练段用 Unsloth 不自造。

### 6.2 关键约束

- 分片必须按域一致性（L1），不能沿用 P-006 的 IID 默认
- 评估必须等算力（L3），三臂对照不足
- 目标模型规模**无实测依据定界**：L5 说明 sub-billion 可装推理能力（但那是**蒸馏**非 SFT，实验在 A100/H100），本集群 MFU / tokens-per-sec **从未实测**（审查成立 5）⇒ 规模待 A-4 基准后定，B-4 的 1.5B 只是候选不是结论
- Studio 训练可用性未验 ⇒ 冒烟须含 Studio 路径（扩 A-1）

### 6.3 风险

| 风险 | 依据 | 缓解 |

| 把"能开箱训练"当"能训出有用模型" | 训练器商品化，价值在数据 | 流程重心放 [2][6] |
